# 開いたときとログインしたときの遅さを減らす（2026-10-11）

作成: 2026-10-11 / Issue #17

## 目的

本人が本番を使って「開いてからの起動が遅い」「ログインしたときも少しカクつく」と感じている。どこで待っているのかを測り、待ちが大きいところから減らす。

## 今の作りで、待ちになりそうなところ

コードを読んで見つけた候補。まだ測っていないので、どれが効いているかは分からない。

### 1つの画面を出すまでに、Supabase Auth へ何度も問い合わせる

- `proxy.ts` → `lib/supabase/middleware.ts` の `updateSession` は、リクエストのたびに `supabase.auth.getUser()` を呼ぶ。`getUser()` は Cookie の JWT を手元で確かめるだけでなく、Supabase Auth のサーバーに毎回問い合わせる
- 画面側でも、データを取る Action がそれぞれ `lib/auth.ts` の `getCurrentUserId()` を呼び、そこでも `getUser()` が走る。ホーム（`app/(app)/page.tsx`）は5つの Action を並べて呼ぶので、`proxy.ts` の1回とあわせて、1画面で6回問い合わせる。並べて呼んではいるが、その分 DB の問い合わせが始まるのが遅れる
- 画像以外の、Next.js が裏で先読みするリクエスト（RSC の prefetch）でも `proxy.ts` が走る

### ホームで、全プレートのウェルを全部読む

`getPlates` は、ウェルの埋まり具合を数えるために、プレートごとに全ウェル（96 Well なら96行）とドロップの数を読む。プレートが増えるほど重くなる。

### サーバーの冷えた起動

Vercel の関数は、しばらく使われないと止まる。久しぶりに開いたときは、関数の起動と、Prisma が DB に繋ぎ直す時間が乗る。Vercel は `hnd1`、Supabase は `ap-northeast-1` で、場所は近い。

### 読み込み中の画面が、`(app)` 全体で1つだけ

`loading.tsx` は `app/(app)/loading.tsx` と `mypage/edit` にしかない。プレートの詳細や設定のページに移るときも、同じ読み込み中の画面になる。

## 進め方

### 1. 測る

直す前に、どこでどれだけ待っているかを数字にする。

- 本番で、ホーム・プレート詳細・ログイン直後のホームを、Playwright で開いて時間を取る（冷えた状態と温まった状態の両方）
- サーバー側は、`getUser()` の1回の時間と、各 Action の DB の時間を、一時的にログに出して Vercel のログで見る。測り終わったら消す
- 冷えた起動は、Vercel のログの `Init Duration` を見る

### 2. 測った結果を見て直す（候補）

効き目が大きいと見込む順。

1. **`getUser()` を、1リクエストに1回にする。** `getCurrentUserId()` を React の `cache()` で包み、同じ描画のあいだは結果を使い回す。安全さは変わらない
2. **`proxy.ts` では `getClaims()` を使う。** JWT の署名を手元で確かめるので、Auth のサーバーに問い合わせない。ただし、プロジェクトの JWT の署名が非対称鍵（JWT Signing Keys）になっている必要がある。今の設定を確かめてから決める。Action 側の `getCurrentUserId()` は `getUser()` のまま残し、守りは緩めない
3. **ホームでは、ウェルの数をまとめて数える。** 全ウェルを読まず、DB で「使っているウェルの数」と「全ウェルの数」を数えて返す
4. **画面ごとに `loading.tsx` を置く。** プレート詳細と設定のページに、それぞれの形をしたスケルトンを出す。待ち時間は変わらないが、押してすぐ反応が見える

冷えた起動は、無料の範囲ではあまり減らせない。測って大きければ、別に考える。

## 結果

### 直す前（2026-10-11、本番）

測定用のアカウント（`plate-lab-perf-20261011@example.com`）を作り、CSV で30枚（24 Well を20枚、96 Well を10枚。ドロップ960）を入れて、Playwright（402px）で7回ずつ測った。中央値。

| 測ったもの | 時間 |
| --- | --- |
| ホームを直接開いて、プレートが見えるまで | 0.93秒 |
| プレートの詳細を直接開いて、ウェルマップが見えるまで | 0.70秒 |
| ホームでプレートを押して、詳細のウェルマップが見えるまで | 1.17秒 |
| サインインを押して、ホームのプレートが見えるまで | 1.33秒 |
| 冷えた状態で `/login` を開いたときの最初の応答 | 2.5秒（温まっていれば 0.5秒） |

分かったこと:

- `getUser()` は、ホームを1回出すのに7回走っていた（`proxy.ts`、`app/layout.tsx` の `getUserSettings()`、ホームの5つの Action）
- 詳細ページは、プレートを取り終えてから、条件とサンプルの見た目を取りに行っていた。`proxy.ts` の認証 → プレート（認証 → DB）→ 条件とサンプル（認証 → DB）と、一列に並んで待つ
- ホームでプレートを押すと、URL が変わるまで 0.34秒、そこからウェルマップが出るまでさらに 0.8秒。データの待ちが大きい
- 本番の JWT は ES256 で署名されていて、`getClaims()` で手元で確かめられる
- `getPlates` はウェルごとにドロップの数（`_count`）だけを読んでいて、思ったより軽い。直さない
- ついでに、`/manifest.webmanifest` が、ログインしていないと `/login` に飛ばされていた（`proxy.ts` の除外が画像だけだった）

### 直したこと

- `lib/auth.ts` — `getUser()` を `cache()` で包んだ `getSessionUserId()` を足し、`getCurrentUserId()` と `getUserSettings()` がそれを使う。1画面で1回になる
- `lib/supabase/middleware.ts` — `getUser()` を `getClaims()` にした。Auth への問い合わせが無くなる
- `app/(app)/plates/[id]/page.tsx` — プレート・条件・サンプルの見た目を並べて取る
- `app/(app)/plates/[id]/loading.tsx` — 詳細の形のスケルトン
- ホームとサンプル画面のプレートを `router.push` から `Link` にした（`ListRow`・`PlateCard` に `href`）。スクショを撮ろうとして、`loading.tsx` も押してからサーバーに取りに行っていて、押してから 0.34秒は何も変わらないことが分かった。`Link` は画面に見えた行の、読み込み中の画面までを先に読んでおくので、押した瞬間にスケルトンが出る
- `proxy.ts` — `webmanifest` を認証の対象から外した

ローカル（本番ビルド）で、登録・取り込み・詳細・Cookie を消すと `/login` に戻ること・サインインし直し・偽の JWT の Cookie では `/login` に戻ることを確かめた。

### 直した後（PR #30、本番、11回の中央値）

| 測ったもの | 直す前 | 直した後 |
| --- | --- | --- |
| ホームを直接開いて、プレートが見えるまで | 0.86〜0.93秒 | 0.78秒 |
| プレートの詳細を直接開く | 0.70秒 | 0.61秒 |
| ホームでプレートを押して、データが出るまで | 1.17秒 | 1.08秒 |
| ホームでプレートを押して、画面が変わり始めるまで | 0.34秒 | すぐ（スケルトン） |
| サインインを押して、ホームのプレートが見えるまで | 1.33秒 | 1.32秒 |

押したときに止まって見えるのは直った。待ち時間そのものは1〜2割縮んだ。

### 残りの内訳（PR #31・#32 で一時的にログを出して測った）

サーバーの中:

| どこ | ふだん | ときどき |
| --- | --- | --- |
| `proxy.ts` の `getClaims()` | 1〜3ms | 150〜170ms（新しいインスタンスで公開鍵を取りに行くとき） |
| `getUser()` | 27〜43ms | 140〜200ms |
| DB の問い合わせ1回 | 4〜9ms | 50〜140ms |
| ホームのデータ取得の全体 | 80〜155ms | 680ms |
| 詳細のデータ取得の全体 | 49〜54ms | 640〜740ms |

ブラウザ（ホームを直接開く）: 接続まで 0.06〜0.17秒、最初の部分（読み込み中の画面）まで 0.04秒、HTML が届き終わるまで 0.4〜0.6秒、そのあと JS（177KB）と描画で約 0.1秒。

分かったこと:

- ふだんはサーバーで 0.05〜0.15秒しか使っていない。残りは、Vercel までの通信と、`proxy.ts` とページを別々の関数として呼ぶ分の行き来で、コードでは減らしにくい
- ときどき 0.6〜0.7秒に跳ねる。そのときは DB の問い合わせ1回が 50〜140ms に伸びている。新しいインスタンスで DB への接続を張り直しているか、Supabase Free の DB が一時的に遅いか
- サインインの 1.3秒は、サインインの Action の中でホームを組み立てる分を含む
- Vercel の Fluid compute は有効で、関数は `hnd1` で動いている。設定で直すところは無い
- 冷えた状態で開くと 2.5秒かかる（関数の起動と DB への接続）。しばらく使わないと起きる

### このあと

コードで縮められるところは、ほぼ縮めた。体感をさらに良くするなら、次のどれか。

- **Service Worker で画面の枠をキャッシュする**: ホーム画面から開いたとき、サーバーを待たずに枠を出す。冷えた起動の 2.5秒に効く。通知（`docs/plans/2026-10-11-notifications.md`）で Service Worker を入れるときに一緒に考える
- **Supabase を有料にする**: DB の跳ねと、7日で止まる問題が無くなる。費用がかかる
- 計測のログは PR #33 で消した。測定用のアカウントは、本人の判断で消す
